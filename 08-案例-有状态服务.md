# 08 - 案例：有状态服务（MySQL 主从复制）

本案例演示如何使用 StatefulSet 部署 MySQL 主从复制集群，涵盖有状态应用的核心模式：稳定标识、独立存储、有序部署。

## 架构设计

```
           ┌──────────────────────────────────────────┐
           │           MySQL Cluster                   │
           │                                          │
  写入 ──► │  mysql-0 (Master)                        │
           │    ├── PVC: data-mysql-0 (10Gi)           │
           │    └── 复制 binlog →                      │
           │                                          │
  读取 ◄── │  mysql-1 (Slave)                         │
           │    ├── PVC: data-mysql-1 (10Gi)           │
           │    └── ← 从 Master 复制                  │
           │                                          │
  读取 ◄── │  mysql-2 (Slave)                         │
           │    ├── PVC: data-mysql-2 (10Gi)           │
           │    └── ← 从 Master 复制                  │
           │                                          │
           └──────────────────────────────────────────┘
                     │
           Headless Service: mysql-headless
           DNS: mysql-{0,1,2}.mysql-headless.webapp.svc.cluster.local
```

**核心需求：**
- Master（mysql-0）接受写入，Slave（mysql-1, mysql-2）只读
- 每个实例独立 PVC，Pod 重启后数据不丢失
- 稳定 DNS 标识，Pod 重启后身份不变

## 第一步：配置与 Secret

```yaml
# 01-config.yaml
apiVersion: v1
kind: Secret
metadata:
  name: mysql-secret
  namespace: webapp
type: Opaque
stringData:
  ROOT_PASSWORD: "RootP@ss2024"
  REPLICATION_PASSWORD: "ReplP@ss2024"
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: mysql-config
  namespace: webapp
data:
  # Master 配置（mysql-0 使用，server-id 由 initContainer 按序号动态生成）
  master.cnf: |
    [mysqld]
    log-bin=mysql-bin
    binlog-format=ROW
    gtid-mode=ON
    enforce-gtid-consistency=ON
    sync-binlog=1
    innodb-flush-log-at-trx-commit=1

  # Slave 配置（mysql-1, mysql-2 使用）
  slave.cnf: |
    [mysqld]
    relay-log=mysql-relay-bin
    read-only=ON
    super-read-only=ON
    gtid-mode=ON
    enforce-gtid-consistency=ON
    log-slave-updates=ON

  # 初始化脚本
  init.sql: |
    -- 创建复制用户
    CREATE USER IF NOT EXISTS 'repl'@'%' IDENTIFIED BY 'ReplP@ss2024';
    GRANT REPLICATION SLAVE ON *.* TO 'repl'@'%';

    -- 创建应用用户
    CREATE DATABASE IF NOT EXISTS appdb CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
    CREATE USER IF NOT EXISTS 'app'@'%' IDENTIFIED BY 'AppP@ss2024';
    GRANT ALL PRIVILEGES ON appdb.* TO 'app'@'%';
    FLUSH PRIVILEGES;
---
# 为 StatefulSet Pod 提供动态打 role 标签的 RBAC 权限
apiVersion: v1
kind: ServiceAccount
metadata:
  name: mysql-sa
  namespace: webapp
---
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: mysql-pod-labeler
  namespace: webapp
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get", "patch", "update"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: mysql-pod-labeler-binding
  namespace: webapp
subjects:
- kind: ServiceAccount
  name: mysql-sa
  namespace: webapp
roleRef:
  kind: Role
  name: mysql-pod-labeler
  apiGroup: rbac.authorization.k8s.io
```

## 第二步：Headless Service

```yaml
# 02-service.yaml
# Headless Service - 为每个 Pod 提供独立 DNS
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
  namespace: webapp
spec:
  clusterIP: None              # Headless
  selector:
    app: mysql
  ports:
  - port: 3306
    targetPort: 3306
    name: mysql
---
# 普通 Service - 供应用读写访问（指向 Master）
apiVersion: v1
kind: Service
metadata:
  name: mysql-rw
  namespace: webapp
spec:
  selector:
    app: mysql
    role: master               # 只匹配 Master Pod
  ports:
  - port: 3306
    targetPort: 3306
---
# 普通 Service - 供应用只读访问（指向所有 Slave）
apiVersion: v1
kind: Service
metadata:
  name: mysql-ro
  namespace: webapp
spec:
  selector:
    app: mysql
    role: slave                # 只匹配 Slave Pod
  ports:
  - port: 3306
    targetPort: 3306
```

## 第三步：StatefulSet

```yaml
# 03-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: webapp
spec:
  serviceName: mysql-headless
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      serviceAccountName: mysql-sa
      # 初始化容器：根据 Pod 序号选择 Master/Slave 配置
      initContainers:
      - name: init-mysql
        image: mysql:8.0
        command:
        - bash
        - -c
        - |
          set -e
          # 根据 Pod 序号设置唯一的 server-id（100, 101, 102...）和角色
          ordinal=${HOSTNAME##*-}
          echo "[mysqld]" > /mnt/conf.d/server.cnf
          echo "server-id=$((100 + ordinal))" >> /mnt/conf.d/server.cnf

          if [ "$ordinal" -eq 0 ]; then
            cp /mnt/config-map/master.cnf /mnt/conf.d/role.cnf
            cp /mnt/config-map/init.sql /mnt/init-scripts/init.sql
            echo "master" > /mnt/labels/role
          else
            cp /mnt/config-map/slave.cnf /mnt/conf.d/role.cnf
            echo "slave" > /mnt/labels/role
          fi
        volumeMounts:
        - name: conf
          mountPath: /mnt/conf.d
        - name: config-map
          mountPath: /mnt/config-map
        - name: init-scripts
          mountPath: /mnt/init-scripts
        - name: labels
          mountPath: /mnt/labels

      # 克隆存量数据容器：首次扩容从库时，从前序节点拉取基础数据与 GTID 位点
      # （注：Percona XtraBackup 属本地物理文件拷贝工具，跨 Pod 物理热备需配合 ncat/ssh + xbstream 流式管道，
      #  或开启 MySQL 8.0.17+ 原生 clone 插件执行 CLONE INSTANCE FROM；中小规模库也可直接用 mysqldump 一致性快照）
      - name: clone-data
        image: mysql:8.0
        command:
        - bash
        - -c
        - |
          set -e
          ordinal=${HOSTNAME##*-}
          if [ "$ordinal" -eq 0 ] || [ -d /var/lib/mysql/mysql ]; then
            exit 0  # Master 或 PVC 已有持久化数据，跳过初始同步
          fi
          # 从前序节点导出 GTID 一致性快照到初始化目录（主容器首次启动时会自动导入 /docker-entrypoint-initdb.d 下的 sql）
          prev_ordinal=$((ordinal - 1))
          source="mysql-${prev_ordinal}.mysql-headless.webapp.svc.cluster.local"
          mysqldump -h "$source" -u root -p"${ROOT_PASSWORD}" \
            --all-databases --single-transaction --triggers --routines --events \
            --set-gtid-purged=ON > /docker-entrypoint-initdb.d/00-clone.sql
        envFrom:
        - secretRef:
            name: mysql-secret
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
        - name: init-scripts
          mountPath: /docker-entrypoint-initdb.d

      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - containerPort: 3306
          name: mysql
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: ROOT_PASSWORD
        - name: REPLICATION_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: REPLICATION_PASSWORD
        resources:
          requests:
            cpu: "250m"
            memory: "512Mi"
          limits:
            cpu: "1"
            memory: "1Gi"
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
        - name: conf
          mountPath: /etc/mysql/conf.d
        - name: init-scripts
          mountPath: /docker-entrypoint-initdb.d
        - name: labels
          mountPath: /etc/labels
        readinessProbe:
          exec:
            command:
            - bash
            - -c
            - |
              mysql -u root -p"${MYSQL_ROOT_PASSWORD}" -e "SELECT 1"
          initialDelaySeconds: 30
          periodSeconds: 10
        livenessProbe:
          exec:
            command:
            - bash
            - -c
            - |
              mysqladmin -u root -p"${MYSQL_ROOT_PASSWORD}" ping
          initialDelaySeconds: 60
          periodSeconds: 15
          failureThreshold: 5
        # 注意：lifecycle 属于容器级（containers[0]）字段
        # 容器启动后：1) 若为从库则配置并启动主从复制；2) 调用 APIServer 给自身 Pod 打上 role 标签
        lifecycle:
          postStart:
            exec:
              command:
              - bash
              - -c
              - |
                ordinal=${HOSTNAME##*-}
                role=$(cat /etc/labels/role)

                # 等待本机 mysqld 启动就绪
                until mysqladmin -u root -p"${MYSQL_ROOT_PASSWORD}" ping --silent; do
                  sleep 2
                done

                # 若为从库（mysql-1, mysql-2），自动指向主库 mysql-0 建立 GTID 复制
                if [ "$ordinal" -ne 0 ]; then
                  mysql -u root -p"${MYSQL_ROOT_PASSWORD}" -e "
                    STOP REPLICA;
                    CHANGE REPLICATION SOURCE TO
                      SOURCE_HOST='mysql-0.mysql-headless.webapp.svc.cluster.local',
                      SOURCE_USER='repl',
                      SOURCE_PASSWORD='${REPLICATION_PASSWORD}',
                      SOURCE_AUTO_POSITION=1,
                      GET_SOURCE_PUBLIC_KEY=1;
                    START REPLICA;
                  "
                fi

                # 使用挂载的 ServiceAccount Token 调用 K8s APIServer 为当前 Pod 打上 role 标签
                # （注：若使用 Oracle Linux Slim 精简版 mysql:8.0 镜像未预装 curl，需在基础镜像中预装或通过 Sidecar 容器执行）
                TOKEN=$(cat /var/run/secrets/kubernetes.io/serviceaccount/token)
                CACERT=/var/run/secrets/kubernetes.io/serviceaccount/ca.crt
                curl -sS --cacert ${CACERT} \
                  -H "Authorization: Bearer ${TOKEN}" \
                  -H "Content-Type: application/strategic-merge-patch+json" \
                  -X PATCH "https://kubernetes.default.svc/api/v1/namespaces/webapp/pods/${HOSTNAME}" \
                  -d "{\"metadata\":{\"labels\":{\"role\":\"${role}\"}}}" > /dev/null

      volumes:
      - name: conf
        emptyDir: {}
      - name: config-map
        configMap:
          name: mysql-config
      - name: init-scripts
        emptyDir: {}
      - name: labels
        emptyDir: {}

  # PVC 模板 - 每个 Pod 独立持久化存储
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: standard
      resources:
        requests:
          storage: 10Gi
```

## 第四步：部署与验证


### 验证主从复制

```bash
# 检查 Master 状态（MySQL 8.0.22+ 推荐 SHOW BINARY LOG STATUS，兼容旧版 SHOW MASTER STATUS）
kubectl exec mysql-0 -n webapp -- \
  mysql -u root -pRootP@ss2024 -e "SHOW MASTER STATUS\G"

# 检查从库复制状态（MySQL 8.0.22+ 使用 SHOW REPLICA STATUS，旧版为 SHOW SLAVE STATUS）
kubectl exec mysql-1 -n webapp -- \
  mysql -u root -pRootP@ss2024 -e "SHOW REPLICA STATUS\G"

# 测试写入
kubectl exec mysql-0 -n webapp -- \
  mysql -u root -pRootP@ss2024 -e "
    CREATE DATABASE testdb;
    USE testdb;
    CREATE TABLE users (id INT PRIMARY KEY, name VARCHAR(50));
    INSERT INTO users VALUES (1, 'Alice');
  "

# 验证数据同步到 Slave
kubectl exec mysql-2 -n webapp -- \
  mysql -u root -pRootP@ss2024 -e "SELECT * FROM testdb.users"

# | id | name  |
# +----+-------+
# |  1 | Alice |
# +----+-------+
```

## Pod 故障恢复

```bash
# Master 故障时：需要手动切换（生产环境建议使用 Orchestrator 等自动化工具）
# 1. 提升 mysql-1 为新 Master（解除 super_read_only 与 read_only）
kubectl exec mysql-1 -n webapp -- \
  mysql -u root -pRootP@ss2024 -e "
    STOP REPLICA;
    RESET REPLICA ALL;
    SET GLOBAL super_read_only=OFF;
    SET GLOBAL read_only=OFF;
  "

# 2. 更新 mysql-0 与 mysql-1 的角色标签（确保 mysql-rw 流量切向新主库）
kubectl label pod mysql-0 -n webapp role=slave --overwrite
kubectl label pod mysql-1 -n webapp role=master --overwrite

# 3. 其他从库（mysql-2）切换到新 Master
kubectl exec mysql-2 -n webapp -- \
  mysql -u root -pRootP@ss2024 -e "
    STOP REPLICA;
    CHANGE REPLICATION SOURCE TO
      SOURCE_HOST='mysql-1.mysql-headless.webapp.svc.cluster.local',
      SOURCE_USER='repl',
      SOURCE_PASSWORD='ReplP@ss2024',
      SOURCE_AUTO_POSITION=1,
      GET_SOURCE_PUBLIC_KEY=1;
    START REPLICA;
  "
```

> **⚠️ 生产架构深度防坑：为什么静态序号脚本在故障切换后暗藏“双主脑裂”风险？**
> 仔细审视上面的 `init-mysql` 与 `postStart` 脚本：它们是通过 **`ordinal == 0`（静态序号是否为 0）** 来硬编码决定谁加载 `master.cnf` 并打上 `role=master` 标签的。
> * **脑裂复现**：当 `mysql-0` 故障、你手动把 `mysql-1` 提升为新 `role=master` 后，一旦 `mysql-0` 所在节点恢复或 Pod 被重新拉起，它的 `initContainer` 和 `postStart` 看到自己名字还是 `mysql-0`，**会无脑把自己的标签再次改回 `role=master` 且开启读写**！此时集群中同时存在 `mysql-0` 和 `mysql-1` 两个带有 `role=master` 标签的实例，`mysql-rw` Service 会把写流量负载均衡发给两个库，瞬间酿成**双主脑裂（Split-Brain）数据损毁事故**！
> * **架构启示（呼应 [01a-CRD与Operator模式](01a-CRD与Operator模式.md) 与 [06a 章](06a-应用打包与多环境管理.md)）**：
>   单纯依靠原生 `StatefulSet + 静态初始化脚本` 只能解决 **Day-1 初始有序部署**，无法安全处理 **Day-2 动态拓扑变更**（因为静态脚本没有全局状态视图）。在生产环境中部署高可用 MySQL，若采用手工运维则切主后不能再用静态序号覆盖标签（应先查询集群内是否已存在带 `role=master` 的存活 Pod）；更推荐直接采用成熟的 **MySQL Operator（如 Percona Operator for MySQL / Oracle MySQL Operator）** 或基于 Raft 协议的 **MGR（MySQL Group Replication）**，由集群内的 Operator Controller 持续感知 GTID 位点与主从拓扑，安全接管故障选主与标签切换。

## 知识点回顾

| 使用的资源 | 作用 |
|-----------|------|
| StatefulSet | 有序部署、稳定标识、独立存储 |
| Headless Service | 为每个 Pod 提供独立 DNS |
| 普通 Service × 2 | 读写分离（rw → Master, ro → Slave） |
| PVC (per Pod) | 独立持久化存储 |
| ConfigMap | MySQL 配置文件 |
| Secret | 数据库密码 |
| Init Container | 根据序号选择配置 |
| Readiness Probe | 健康检查，影响 Service 路由 |
